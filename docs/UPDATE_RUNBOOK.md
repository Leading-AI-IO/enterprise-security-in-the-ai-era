## この手順書が守っているもの

本書が本文（序章「本書は更新される」、付録A-6、付録B-4、終章「更新の場所」）で宣言している運用は5つある。**手順はすべてこの5つを実装するために存在する。**

1. **一次資料を著者が開いて文言を確かめた行だけを数える** ── AI調査ツールの出力、報道、二次資料だけで階層T1・T2を付けない。確かめていない行はT3として台帳に残し、集計に入れない
2. **提言の文言は一次資料のまま保つ** ── 調査結果の要約が一次資料の文言と違えば、本文の文言に差し替え、差し替えた事実を `issuer` 列に記す
3. **追記専用** ── 行を削除も書き換えもしない。統合は `merged_into` に統合先を書く。訂正は、訂正である旨と日付を明記して追記する
4. **更新の場所は3か所に限る** ── 提言台帳 `data/proposals.csv`、付録B（検証記録）、終章の指標表。本文の文章そのものを変えるときは、変更箇所の直前に「（YYYY年M月D日追記／訂正）」を置く
5. **全コミットに署名、秘密鍵はリポジトリに入れない** ── 姉妹書の手順書と同じ

手順の途中で迷ったら、その操作が上の5つのどれを守るためのものかに戻ること。

## 0. 作業前の確認（毎回）

```powershell
cd <リポジトリのクローン先>
git remote -v
git fetch origin
git log --oneline HEAD..origin/main
git status
git config --get pull.rebase
Get-ChildItem -Recurse -File -Include *.asc,*.rev,*.gpg,*.key,*.pgp
```

- `git remote -v` に `enterprise-security-in-the-ai-era.git` が表示されること
- `git log --oneline HEAD..origin/main` の出力が空であること（空でなければ `git pull --no-rebase --no-edit`）
- `git status` が `nothing to commit, working tree clean` であること
- `pull.rebase` が `false` であること
- 最後のコマンドが何も表示しないこと

## 1. 提言を追加する場合

### 1-1. 一次資料に到達する

発行元のドメイン上の文書（HTMLまたはPDF）を、著者が自分で開いて読む。AI調査ツールの出力、報道記事、まとめサイト、他者の要約は、到達の根拠にしない。

到達できない場合は、行を起こしてよいが階層はT3とし、`issuer` 列に「未開封」と到達できなかった理由を書く。T3の行は本文の集計に入らない。

### 1-2. 記録する内容を揃える

列の定義は付録A-2にある。一次資料から、次を揃える。

| 列 | 規律 |
|---|---|
| `new_id` | 発行元の種類の記号（A〜H）と3桁の連番。既存の番号は使い回さない |
| `type` | 発行元の種類（A 政府・公的機関／B 標準団体／C AI企業／D セキュリティ企業／E 保険／F 学術／G 個人の有識者／H 規制当局）。定義は第4章 |
| `proposal` | 一次資料の文言を引用符で囲んで逐語で。日本語訳または要約を括弧で添える |
| `issuer` | 発行元、資料名、日付。開封の記録（日付、全文か抜粋か）を必ず残す |
| `tier` | 文言と根拠（データの出所、母数、方法）が同じ資料にあればT1。文言はあるが根拠がなければT2。開けていなければT3 |
| `k` | 提言の種類（K1〜K9）。主分類を先に書き、副分類を「/」「・」「,」で続ける。定義は第6章 |
| `evidence` | 根拠の有無と内容。なければ「なし」 |
| `status` | 提言どまり／制度化済み／効果測定あり、など。「効果測定あり」は、効果を測った記述が同じ資料にあるときだけ |
| `limits` | 発行元自身または第三者が書いた限界・批判。なければ「—」 |
| `route` | 日本の台帳の侵入経路との対応。複数あれば「・」で並べる。侵入経路を書かない公表文への処方は「経路非開示への処方」 |
| `urls` | 開いた一次資料のURL |

### 1-3. 数え直す

```powershell
python scripts/count_proposals.py
```

出力の件数（集計対象、効果測定あり、K別、K5の発行元の種類、経路別）を控える。

### 1-4. 本文に反映する

本文の件数は、次の場所だけで更新する。

- 各章冒頭の「第N版時点」の表（第1章・第4章・第6章など）
- 終章の指標表に、新しい版の列を足す（既存の列は書き換えない）
- READMEのProposalsバッジ・Last Updatedバッジ・更新履歴、`llms.txt` の冒頭の件数

本文の文章で件数に触れている箇所は、書き換えず、直前に「（YYYY年M月D日追記）」を置いて新しい値を書く。第1版の記述は残す。

### 1-5. コミットして push

```powershell
git add data/proposals.csv docs/ README.md README_en.md llms.txt
git commit -S -m "Add proposals <new_id>..<new_id>: <発行元>"
git log --show-signature -1
git push origin main
```

`git log --show-signature -1` に `Good signature` が出ることを確認してから push する。

## 2. 階層を変える場合（T3の行を開いた、T2の根拠を見つけた）

行は書き換えない。次を行う。

1. `tier` 列の値を変える。`issuer` 列の末尾に「（YYYY年M月D日 T3→T1：<開いた資料と確認した文言>）」のように、日付・変更前後・根拠を追記する
2. 調査結果の要約が一次資料の文言と違っていた場合は、`proposal` 列を本文の文言に差し替え、差し替えた旨を `issuer` 列に記す（第1版のA-063「前倒し」の例を参照。付録A-3）
3. 階層の変更で集計対象の件数が変わるので、1-3と1-4を行う

コミット件名は `Upgrade tier A-087: T3→T1`。

T1・T2からT3へ下げることは、原則として行わない。一次資料が消えた場合は、`issuer` 列に到達できなくなった日付を追記し、階層は変えない。

## 3. 既存の行を訂正する場合（誤りを指摘された、発行元が訂正した）

1. 該当行の `limits` 列または `issuer` 列の末尾に、`（YYYY年M月D日訂正）` に続けて、何がどう変わったか、根拠の一次URL、指摘者の名（本人の希望があれば）を追記する。元の値は残す
2. 本文中で元の値に触れている箇所の直前に `（YYYY年M月D日訂正）` を置き、改行して訂正文を書く
3. 訂正の対象が「数字の状態」（確認済み／出所不明／発行元が否定など）なら、付録B-1の該当行の「確認の経緯」に日付つきで追記し、「状態」を更新する。行は消さない。新しく否定された数字、一次資料に届かなかった数字が出たら、B-1に行を足す

コミット件名は `Correct row E-010: <内容>`。

## 4. 付録Bと終章の指標表を更新する場合

- **付録B-1**：数字の状態が変わったら、変わった日付と根拠を「確認の経緯」に追記する。状態の名称はB-2の定義から選ぶ。定義にない状態が必要になったら、B-2に行を足す
- **付録B-5**（第9章の公表文の分類）：姉妹書の台帳に行が増えたら、同じ基準（上限で知らせた／記録で絞った／件数を書けなかった／どちらとも読めない）で分類し、日付つきの別表として追加する。既存の表は直さない
- **終章の指標表**：版ごとに列を足す。16の指標のうち、台帳から機械的に数えられるもの（1〜4）は `scripts/count_proposals.py` の出力を使い、本文で確認するもの（5・6・14）と姉妹書の台帳から数えるもの（8〜12）は、確認した日付を列の見出しに書く。指標13（初報で「上限」「確認」の別を明記した公表文）は第1版で未集計であり、数えたら値を入れる

## 5. 版を上げる場合

台帳の行数が大きく変わったとき、提言の種類（K）や階層の判定基準を変えたとき、第3部・第4部の提言の文言を変えたときに版を上げる。

- READMEの更新履歴、`llms.txt` の冒頭、各章冒頭の「第N版時点」の見出しを更新し、GitHubのReleasesに版を作る
- 第1版の数字に触れる箇所は、（YYYY年M月D日追記）を前置して追記し、第1版の記述は残す
- 章の提言（第7〜12章の冒頭の太字の1文）を変える場合は、変えた理由を終章「主張を、確かめた事実だけで組み直す」の直後に日付つきで書く。本書の主張の1文（序章・終章）を変える場合は、版を上げ、変えた理由をREADMEの更新履歴にも書く

## 6. 失敗時の対応

姉妹書『The Japan Breach Registry 2026』の `docs/UPDATE_RUNBOOK.md` 第5節と、『The AI Forecast Registry』の手順書の付録A〜Cを、そのまま適用する（コミットメッセージの誤り、内容の誤り、署名の失敗、秘密鍵の混入、pushの拒否）。本書に固有の失敗は次の2つである。

**本文の件数だけを直し、台帳を直さなかった（またはその逆）。** `python scripts/count_proposals.py` を実行し、出力と本文の「第N版時点」の表・終章の指標表が一致することを確かめてからコミットする。一致しない箇所があれば、台帳を正として本文を追記で直す。

**一次資料を開かずに階層をT1・T2にした。** 気づいた時点で、その行の `issuer` 列に「未開封」と日付を追記し、階層をT3に戻す。本文の件数を1-3・1-4の手順で数え直す。開いて確かめてから、第2節の手順で再度上げる。
